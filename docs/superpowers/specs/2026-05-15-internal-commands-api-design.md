# Internal Commands API — Design

**Date:** 2026-05-15
**Status:** Approved for planning
**Author:** Allen Tuh (with Claude)

## Goal

Expose a small, stable, typed programmatic API that lets other oclif plugins
loaded into `sdkck` enumerate the commands available at runtime. The API hides
oclif's internal types from consumers and applies sdkck-specific filtering
(permission allowlist, sensitive-command denylist) so plugins don't have to
re-implement that logic.

## Non-Goals

- Running commands programmatically — namespace reserved (`sdkck.commands.run`)
  but not implemented in this spec.
- Searching commands — namespace reserved (`sdkck.commands.search`) but not
  implemented.
- Lifecycle event subscriptions.
- A CLI-surfaced version of this API (e.g. `sdkck commands list --json`).
- Enumerating JIT plugins that haven't been installed yet.

## Consumer Shape

```ts
import {sdkck} from 'sdkck'

// inside a command/hook in another oclif plugin:
const cmds = sdkck.commands.list(this.config)
// → Array<CommandInfo>
```

`sdkck` is a named export from the package root (`dist/index.js`). Its only
populated namespace today is `.commands`, which exposes one function: `list`.

## Public Types

```ts
export interface CommandArg {
  name: string
  required: boolean
  description?: string
}

export interface CommandFlag {
  name: string
  type: 'boolean' | 'option'
  required: boolean
  multiple: boolean
  description?: string
}

export interface CommandInfo {
  /** Canonical colon-separated id, e.g. "api:import". */
  id: string
  /** Space-separated id matching sdkck's display style, e.g. "api import". */
  displayId: string
  summary?: string
  description?: string
  hidden: boolean
  /** Owning plugin name, e.g. "sdkck", "@hesed/jira". */
  pluginName?: string
  /** Plugin source type from oclif's plugin metadata. */
  pluginType?: 'core' | 'user' | 'link' | 'jit'
  /** True for commands generated by `api import` (OpenAPI/Postman/GraphQL ops). */
  isDynamic: boolean
  /** False if the permission allowlist blocks this command. */
  isPermitted: boolean
  /** True if classified as sensitive (auth/credentials/etc.). */
  isSensitive: boolean
  args: CommandArg[]
  flags: CommandFlag[]
  aliases: string[]
  /** First segment of the id, e.g. "api" for "api import". */
  topic?: string
}

export interface ListCommandsOptions {
  /** Include commands flagged `hidden`. Default: false. */
  includeHidden?: boolean
  /** Include commands blocked by the permission allowlist. Default: false. */
  includeDisallowed?: boolean
  /** Include commands classified as sensitive. Default: false. */
  includeSensitive?: boolean
  /** Restrict to a single topic (first id segment). */
  topic?: string
}
```

All returned objects are deeply frozen (`Object.freeze`) so consumers cannot
mutate sdkck's internal state through them.

## Module Layout

- **New:** `src/api.ts` — defines `CommandInfo`, `ListCommandsOptions`, the
  `sdkck` object, and the `list()` implementation. Internal helpers:
  `toCommandInfo(cmd, config, ctx)`, `isSensitiveCommand(cmd)`,
  `SENSITIVE_SEGMENTS` constant.
- **Modified:** `src/index.ts` — adds `export {sdkck} from './api.js'` and
  re-exports the types `CommandInfo`, `CommandArg`, `CommandFlag`,
  `ListCommandsOptions`.
- **Modified:** `src/api-dynamic-commands.ts` — when generating dynamic
  commands, attach a stable marker `static __sdkckDynamic = true` on the
  generated class so `list()` can detect them without string-matching ids.
- **Modified:** `src/commands/api/auth.ts` — add `static sensitive = true` to
  make the classification explicit (not just pattern-matched).

## Sensitive Command Filtering

Default behavior: `list()` excludes sensitive commands. Classification rules,
in this precedence order:

- If the command class has `static sensitive` defined (true or false), that
  value wins.
- Otherwise, the pattern fallback below decides.

1. **Explicit opt-in on the command class:**

   ```ts
   export default class ApiAuth extends Command {
     static sensitive = true
   }
   ```

   `list()` reads `(CmdClass as any).sensitive` from the loadable metadata.

2. **Pattern fallback** — any command whose id contains a segment in this set
   is treated as sensitive:

   ```ts
   const SENSITIVE_SEGMENTS = new Set([
     'auth', 'credential', 'credentials',
     'login', 'logout',
     'secret', 'secrets',
     'token', 'tokens',
   ])
   ```

   Matching is per id-segment (split by `:`), case-insensitive. So `api:auth`
   matches, but `authority` would not (no exact segment match).

3. **Escape hatch** — setting `static sensitive = false` opts a command out of
   the pattern fallback. Useful when a command's id contains a false-positive
   segment (e.g. an id incidentally containing `login` that isn't sensitive).

`isSensitive` in the returned `CommandInfo` reflects the combined
classification, regardless of whether the command was filtered out.

## Permission Filtering

Reuses `loadPermissionConfig` and `isCommandAllowed` from
`src/permission-config.ts` — the same code path the init hook uses. This
ensures behavior matches `sdkck help` exactly. By default disallowed commands
are filtered out; `includeDisallowed: true` returns them with
`isPermitted: false`.

## Detection of Dynamic Commands

`api-dynamic-commands.ts` already builds command classes at runtime from
stored OpenAPI operations. We add `static __sdkckDynamic = true` to each
generated class. `list()` checks `(CmdClass as any).__sdkckDynamic === true`
to set `CommandInfo.isDynamic`.

## Filtering Order

For each entry in `config.commands`:

1. Build raw `CommandInfo` from the loadable metadata (no class load required
   for most fields). Load the class lazily only to read static props
   (`sensitive`, `__sdkckDynamic`).
2. Apply topic filter if set; skip if not matching.
3. Apply hidden filter unless `includeHidden`.
4. Apply permission filter unless `includeDisallowed`.
5. Apply sensitive filter unless `includeSensitive`.
6. Freeze and emit.

Sort the final array by `displayId` ascending so consumers get a stable order.

## Loading Cost

`config.commands` returns `Command.Loadable[]` — metadata-only, no class
instantiation. Reading `static sensitive` requires `cmd.load()`, which is the
same call oclif uses internally. For a typical sdkck install this is on the
order of dozens of commands; load is cached by oclif. If profiling later shows
this is a hot path, we can cache `CommandInfo[]` keyed by `config.version` +
plugin signature, but that's out of scope here.

## Error Handling

`list()` is read-only and side-effect free. If a single command fails to load
(e.g. corrupted JIT install), the error is caught, logged via the existing
`file-logger`, and that one command is omitted from the result. The function
never throws.

## Tests

`test/api.test.ts`:

- Returns expected entries for a stub config with 3 commands.
- `includeHidden: false` hides hidden commands; `true` includes them and they
  appear with `hidden: true`.
- Permission allowlist filters by default; `includeDisallowed: true` returns
  blocked commands with `isPermitted: false`.
- `api:auth` (and any command with `static sensitive = true`) is excluded by
  default; `includeSensitive: true` includes it with `isSensitive: true`.
- A command id matching the pattern denylist (e.g. `foo:login`) is excluded
  by default.
- A command with `static sensitive = false` overrides the pattern denylist
  (returned by default).
- `topic: 'api'` returns only commands whose id starts with `api:`.
- `displayId` matches `toConfiguredId(id, config)`.
- Dynamic commands (`static __sdkckDynamic = true`) get `isDynamic: true`.
- A load failure on one command does not prevent the rest from being
  returned.
- Returned objects are frozen (mutating throws in strict mode).
